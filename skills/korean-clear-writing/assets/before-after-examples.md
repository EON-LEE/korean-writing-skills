# 수정 예시

모든 사례는 가상 예시다. 예시의 대상·조건·담당자·수치를 사용자 문서에 추가하지 않는다. 수정 전 문장만으로 확인할 수 없는 정보는 별도로 제공된 입력이라고 표시한다.

## 1. 조건과 순서

입력: 자동 저장이 꺼져 있으면 켜야 한다. 설정 저장 후 프로그램을 재시작해야 한다.

수정 전: 자동 저장이 꺼진 경우 활성화 및 저장 후 재시작을 진행해 주세요.

수정 후:

1. 자동 저장이 꺼져 있으면 자동 저장을 켜세요.
2. 설정을 저장하세요.
3. 프로그램을 다시 시작하세요.

이유: 조건을 먼저 제시하고 독립적인 행동을 분리했다. 원문의 실행 순서를 유지했다.

## 2. 미확인 담당자

수정 전: 검토 후 반영 예정이다.

수정 후: 검토가 끝난 뒤 반영할 예정이다.

확인 필요: 검토 담당자, 반영 담당자, 반영 대상.

이유: 알려지지 않은 담당자를 만들어 넣지 않는다. 문장 수정만으로 책임의 공백이 해결됐다고 주장하지 않는다.

## 3. 다른 개념의 보존

입력: 운영팀이 배포안을 검토하고 보안팀이 승인한다.

잘못된 수정: 담당 팀이 배포안을 확인한다.

올바른 수정:

1. 운영팀은 배포안을 검토한다.
2. 보안팀은 배포안을 승인한다.

이유: 검토와 승인은 다른 행동이다. 두 행위자의 책임을 유지한다.

## 4. 명사 연결

입력: 고객 데이터에 새 보안 정책을 적용할지 검토한다.

수정 전: 고객 데이터 보안 정책 적용 검토를 실시한다.

수정 후: 고객 데이터에 보안 정책을 적용할지 검토한다.

이유: 조사와 서술어로 대상과 행동의 관계를 밝혔다.

## 5. 진행과 완료

수정 전: 운영팀은 설정 변경 사항에 대한 검토를 진행하고 있는 상황이다.

수정 후: 운영팀은 설정 변경 사항을 검토 중이다.

잘못된 수정: 운영팀은 설정 변경 사항을 검토했다.

이유: 진행 상태를 간결하게 표현하되 완료로 바꾸지 않는다.

## 6. 동시 행동

입력: 두 버튼은 동시에 눌러야 한다.

수정 전: A 버튼과 B 버튼을 동시에 누르세요.

수정 후: A 버튼과 B 버튼을 동시에 누르세요.

이유: 이미 명확하며 동시 수행 예외에 해당한다. 순차 단계로 분리하지 않는다.

## 7. 전문용어

입력: 독자가 RAG라는 약어에 익숙하지 않다.

수정 전: RAG로 답변을 생성한다.

수정 후: 검색 증강 생성(RAG)은 검색한 자료를 활용해 답변을 생성하는 방식이다.

이유: 전문용어는 유지하고 독자에게 필요한 개념을 설명한다. 실제 문서의 기술적 정의와 범위는 해당 출처로 확인한다.

## 8. 사실과 가설

수정 전: 이 기능을 적용하면 처리 시간이 크게 줄어들 것으로 예상한다.

수정 후: 이 기능이 처리 시간을 줄일 것으로 예상한다. 감소 폭은 확인이 필요하다.

잘못된 수정: 이 기능은 처리 시간을 30% 줄인다.

이유: 기대를 측정 결과로 바꾸거나 임의 수치를 추가하지 않는다.

## 9. 안전 조건

수정 전: 장비가 식기 전에는 만지지 마세요. 뜨거운 부품은 화상을 일으킬 수 있습니다.

수정 후:

**경고:** 장비가 식기 전에는 만지지 마세요. 뜨거운 부품은 화상을 일으킬 수 있습니다.

확인 필요: 실제 절차에 필요한 냉각 완료 판단 기준.

이유: 부상 위험과 금지 조건을 보존한다. 임의의 온도나 대기 시간을 추가하지 않는다.

## 10. 형식 선택

입력: 실제 문서에 있는 세 대안의 비용, 효과, 제약을 비교해 달라는 요청.

선택: 같은 비교 기준을 열로 둔 표. 비용이 확인되지 않은 항목은 “확인 필요”로 표시한다.

선택하지 않음: 불필요한 웹앱·설명 영상 제작. 누락 비용을 0으로 기입.

이유: 모든 형식을 검토하되 비교 목적에는 표가 충분하다.
